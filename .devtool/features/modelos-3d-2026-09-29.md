# Modelos 3d

## 1. Modelo de datos

Ahora `meshRenderer.meshRef` acepta primitivas o URLs arbitrarias en `types.ts`\](/home/fernando/gitProjects/webxr-platform/src/lib/ecs/types.ts). Conviene evolucionarlo a algo explícito:

```
type MeshRef =
  | { kind: 'builtin'; id: 'box' | 'sphere' | 'plane' | 'ground' }
  | { kind: 'asset'; assetId: 'sha256:...' };
```

El `assetId` debe ser un hash de contenido. Si el archivo cambia, nace otro asset.

La escena podría incluir solo:

```
{
  "assetId": "sha256:abc123",
  "type": "model",
  "variant": "lod0"
}
```

Nunca debería incluir:

- El binario.
- Una URL temporal firmada.
- Una URL `blob:`.
- Una referencia a `localInventoryItemId` como mecanismo de resolución.

El manifiesto del asset sí puede existir como metadato separado:

```
interface AssetManifest {
  assetId: string;
  type: 'model';
  format: 'glb';
  mimeType: string;
  byteSize: number;
  dependencies: string[];
  bounds: { min: Vec3; max: Vec3 };
  lods?: string[];
  collision?: {
    kind: 'box' | 'capsule' | 'convex' | 'mesh';
    assetId?: string;
  };
}
```

Preferiría `.glb` autocontenido para evitar que un modelo dependa de varias texturas externas.

## 3. Inventario local

El adaptador actual `local.ts`\](/home/fernando/gitProjects/webxr-platform/src/lib/inventory/adapters/local.ts) solo tiene stores para `items` y `folders`.

Habría que añadir conceptualmente:

```
assets
assetReferences
uploadQueue
```

El `InventoryItem` conservaría el `slotData`, pero los slots apuntarían a hashes. Los bytes se guardarían aparte:

```
assetId -> Blob
```

Esto permite:

- Reutilizar el mismo modelo en muchos objetos.
- No duplicar blobs al clonar.
- Detectar archivos corruptos mediante hash.
- Saber qué assets deben transferirse al publicar o compartir.

## 4. Sesión con host local

Este es el caso más importante.

Si alguien aloja un mundo usando un modelo de su inventario local, otro usuario no puede acceder a su IndexedDB. Por tanto:

1. El host envía rápidamente el snapshot de escena.
2. El invitado crea todos los slots con placeholder.
3. El invitado calcula qué `assetId` no tiene en caché.
4. Solicita esos assets al host.
5. El host los envía por un canal WebRTC dedicado.
6. El invitado verifica el hash.
7. Se reemplaza el placeholder por el modelo real.
8. El modelo se guarda en caché local.

No usaría el canal actual de snapshots para los binarios. `peerConnection.ts`\](/home/fernando/gitProjects/webxr-platform/src/lib/xr/net/peerConnection.ts) está diseñado para JSON fragmentado, con límite de mensajes y control de estado. Los modelos deben ir por un canal independiente:

```
world-sync       -> snapshots, interacciones y lógica
world-state      -> transforms y presencia
asset-control    -> manifests, requests, acknowledgements
asset-data       -> chunks binarios
```

El canal de assets debería incluir:

- Chunks binarios de 64–128 KB.
- Backpressure usando `bufferedAmount`.
- Cola con prioridad.
- Cancelación.
- Reintentos.
- Confirmación por hash.
- Límite de descargas simultáneas.
- Expiración de requests.

El host no debería transferir todos los modelos al entrar un usuario. Solo los que el cliente pida o los que sean prioritarios.

## 5. Carga deferred sin bloquear el juego

En `sceneGraph.ts`\](/home/fernando/gitProjects/webxr-platform/src/lib/xr/sceneGraph.ts), `createMesh()` es actualmente síncrono y crea únicamente primitivas. El nuevo flujo debería separar:

```
Slot lógico
  └── TransformNode inmediato
       ├── Placeholder visual
       ├── Collider ligero
       └── Modelo real cuando esté disponible
```

El `TransformNode` y la lógica del objeto existen desde el primer frame. Solo se retrasa la representación pesada.

Prioridades recomendadas:

1. Modelos agarrados o cercanos al usuario.
2. Modelos visibles en cámara.
3. Modelos que tengan interacción o collider.
4. Modelos cercanos a portales.
5. Resto de modelos en segundo plano.

Además:

- Máximo 1–2 decodificaciones simultáneas.
- Cachear un único `AssetContainer` por hash.
- Instanciar clones visuales desde ese contenedor.
- Descargar LOD bajo primero cuando exista.
- Liberar modelos lejanos bajo presión de memoria.
- Mantener colliders simples aunque el modelo visual todavía no haya llegado.
- Si falla una descarga, mantener placeholder y registrar el error sin romper la escena.

## 6. Hosting cloud y mundos publicados

Antes de publicar o alojar persistentemente un mundo:

1. Recorrer la escena y obtener el cierre completo de assets.
2. Detectar cuáles son locales.
3. Subirlos al object storage.
4. Verificar hash, tamaño y tipo MIME.
5. Crear las relaciones del mundo con esos assets.
6. Solo entonces guardar o publicar la revisión.

El mundo publicado debe quedar completamente autosuficiente. No puede depender de:

- El inventario local del creador.
- Una URL temporal.
- Una revisión mutable del inventario.
- Un `worldLineageId` sin sus assets.

Las revisiones de `publications.ts`\](/home/fernando/gitProjects/webxr-platform/src/lib/server/services/publications.ts) deberían incluir o poder resolver un `assetSet` inmutable. Si se elimina posteriormente el asset original del inventario, la publicación debe seguir funcionando.

## 7. Clonado e instanciación

### Clonar localmente

Se copia el `SlotTree`, pero se reutilizan los blobs por `assetId`. No se duplican físicamente.

### Clonar de cloud a local

Se descargan los modelos de forma lazy o mediante una opción “descargar para uso offline”.

### Clonar de local a cloud

Debe ejecutarse una promoción:

```
Local IndexedDB
  -> hash y validación
  -> upload presignado
  -> asset cloud
  -> nueva relación con el mundo
```

### Instanciar desde snapshot

El snapshot debe contener referencias a assets y su manifiesto, pero no depender de su origen original. Un snapshot publicado debe tener assets cloud; uno local puede tener una política de transferencia desde el host.

### World portals

Los portales son especialmente delicados porque `WorldPackage`\](/home/fernando/gitProjects/webxr-platform/src/lib/worlds/types.ts) puede contener otros mundos. Al crear un portal hay que calcular recursivamente sus dependencias:

```
World A
  -> Portal B
      -> Portal C
          -> Model X
```

El host debe poder:

- Transferir esos assets desde su máquina.
- O promoverlos a cloud antes de hacer público el portal.

La propiedad `source` puede seguir sirviendo para mostrar procedencia, pero nunca debe ser el mecanismo mediante el cual otro cliente intenta leer el inventario del creador.

## 8. Persistencia cloud recomendada

Añadiría conceptualmente estas entidades:

```
Asset
- id/hash
- type
- mimeType
- byteSize
- storageKey
- status
- createdAt

AssetOwner
- assetId
- ownerId

WorldAsset
- worldId o revisionId
- assetId
- required

SessionAsset
- roomCode
- assetId
- availability: cloud | host-local
```

El blob estaría en object storage con una clave como:

```
assets/sha256/ab/cd/abcdef...
```

Esto permite deduplicación global y evita copiar físicamente el mismo modelo cuando varios mundos lo utilizan.

## 9. Estados de disponibilidad

Cada mundo debería poder indicar una de estas situaciones:

```
local-only
session-transferable
cloud-backed
published
missing-assets
uploading
```

Ejemplos:

- Un mapa local solo: `local-only`.
- Un mapa local alojado temporalmente: `session-transferable`.
- Un mapa alojado con assets promovidos: `cloud-backed`.
- Una revisión pública: `published`.
- Un mapa importado cuyo archivo fue eliminado: `missing-assets`.

Esto permite mostrar errores claros antes de publicar o iniciar una sesión.

## Decisión clave

No intentaría resolver todos los casos con una única URL de modelo.

La solución robusta es:

```
AssetRef por hash
        +
AssetResolver
        +
AssetStore local/cloud
        +
transferencia WebRTC temporal desde el host
```

Así un mundo puede funcionar en modo local, en una sesión multiplayer, como mundo persistente y como publicación sin cambiar la estructura de la escena ni enviar modelos pesados dentro del JSON.
